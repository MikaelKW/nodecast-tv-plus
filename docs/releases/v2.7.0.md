# NodeCast TV Plus v2.7.0

v2.7.0 adds administrator diagnostics and reviewed support snapshots, improves source-setting reliability, and includes dependency updates.

---

### Highlights

- **Settings > Diagnostics** shows application version/revision, process resources, managed playback sessions, source synchronization results, and recent events. Access is restricted to administrators in both the interface and server API ([#426]).
- Playback events for Live TV, Movies, and Series explain the selected path and important start, failure, recovery, replacement, and cleanup events. Generated account-bound trace IDs connect events from the same attempt, including long playback sessions and manual starts ([#426]).
- Prepare and review a small support snapshot, then explicitly download the exact text shown. Its fixed allowlist excludes provider URLs, credentials, personal information, and raw logs. Nothing is uploaded automatically, and leaving Diagnostics or losing access clears the preview ([#426]).
- Overlapping source-setting changes no longer silently replace one another. Successful changes persist, while changes that cannot be applied fail explicitly ([#453]).
- Earlier asynchronous Movie or Series requests cannot replace the latest playback selection ([#426]).
- Dependencies have been updated alongside the existing protected validation paths.

Read the [Diagnostics guide](https://github.com/MikaelKW/nodecast-tv-plus/blob/main/docs/DIAGNOSTICS.md) for event interpretation, retention, and safe snapshot sharing.

---

### Upgrade from v2.6.2

Back up `/app/data`, pull the release image from either registry, and recreate the container with the same data volume and deployment secrets:

```bash
docker pull ghcr.io/mikaelkw/nodecast-tv-plus:2.7.0
```

or:

```bash
docker pull mikaelkw/nodecast-tv-plus:2.7.0
```

No manual database migration is required. Preserve the existing strong, distinct `JWT_SECRET` and `SESSION_SECRET` values, and preserve `TOTP_ENCRYPTION_KEY` when authenticator-app 2FA is in use.

Stable tags for this release are `2.7.0`, `2.7`, and `latest`. The `2.6` tag remains on the previous release line.

To roll back, stop the upgraded container, restore the pre-upgrade data backup, and recreate the container with 2.6.2 and the original deployment secrets. Do not assume that simply starting an older image against upgraded data is a safe rollback.

### Validation

Release gates cover overlapping source changes, playback correlation and replacement, authorization, account/session changes, bounded event retention and export size, redaction, and diagnostics failures without playback interruption.

Combined validation includes application and browser/media behavior, mobile WebKit, physical iPhone Safari, reverse-proxy subpaths, dependency and runtime-image checks, CodeQL, container health, and supported migrations. The migration gate targets upstream v2.1.1 and v2.1.4 and published Plus v2.6.2. Final published images are verified for both `linux/amd64` and `linux/arm64` and matching registry aliases.

### Known limitations and deferred follow-up

- Diagnostics are a recent in-memory view, not persistent audit logging or historical monitoring. Events are limited to 128 entries and expire after one hour; restarting the application clears the history.
- Resource values describe the application process, not total host or container usage. Direct and browser-remuxed playback appear in events rather than the managed-session card.
- Support snapshots are limited to 48 KiB, 50 events, 20 source status entries, and 16 managed sessions. Always review the preview before sharing it. Screenshots and separate logs are not covered by the snapshot's allowlist.
- Broader playback unification, durable background jobs, storage migrations, notifications, and TypeScript migration remain separate work.
- Hardware acceleration still depends on suitable hardware, drivers, and container configuration. Capability detection alone does not establish real-device operation; broader functional encoder checks remain tracked in [#77].
- The intermittent empty-channel-list report remains tracked in [#361]; this release does not claim to resolve it.
